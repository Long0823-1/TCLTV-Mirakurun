# 実機検証（2026-10-28）

対象: TCL G06 / MT5867、Android 11、ARMv7、Linux 4.19.116+、Magisk root。
対応するベンダーライブラリーのSHA-256は `android/assets/setup.sh` に固定しています。
Windows PCから有線LANとWi-Fiの各TVアドレスへ接続して確認しました。

## 確認できた項目

- APKをビルドし、APK Signature Scheme v2/v3署名を検証。
- APKから新しいLinux実行環境を展開し、TVの登録局から11多重の地デジ設定を作成。
  この実機には既存のネイティブチューナー配信環境があり、それを検出して利用しました。
- Mirakurun 4.1.5 / Node.js 22.23.4 / Python 3.12で起動。
- `/api/status`、`/api/version`、`/api/tuners`、`/api/services`、`/api/programs` の応答。
- 41サービスの検出、番組情報の取得（テスト中に1,636番組を確認）。
- NHK総合と日テレの異なる多重を2チューナーで同時配信。
  同時リクエスト時に両チューナーの `isUsing=true`、`isFault=false` を確認。
  約40秒の受信でそれぞれ68,350,596 / 78,549,972バイトを受信し、
  FFmpegで両方のMPEG-2映像を10フレーム以上デコード。
- アプリの停止操作でサーバープロセス停止と自動起動フラグ削除を確認。
- 起動操作でforeground serviceとCPU wake lockを取得。
- TV再起動後、アプリを手動で開かずにMirakurunとforeground serviceが復帰。
  有線LAN側のAPI応答と保存済みサービス一覧の復帰を確認。
- 電源ボタン相当の `KEYCODE_POWER` を送信し、`mWakefulness=Asleep` / display OFFを確認。
  その状態で有線LANから約60秒のNHK総合配信を継続し、114,101,148バイトを受信。
  消灯中の受信データの45秒地点から映像を10フレームデコード。
- Wi-FiのIP取得が起動より遅い場合、標準Mirakurunの待受けアドレスに含まれない問題を発見。
  IPv4を0.0.0.0で待ち受ける互換パッチを追加し、既存のIP・Originアクセス制限を維持。
  修正後、有線側とWi-Fi側でHTTP 200 / APIの4.1.5応答を確認。
- CRC-32 / CRC-32Cの既知ベクトルとCRC-32の分割入力を検証。
- 同梱rootfsに実機の接続キー、局設定、番組・サービスDB、/proc、/devがないことを検査。
- v0.1.1で環境削除ボタンを追加。削除対象を隔離した実機上のテスト用ディレクトリへ
  置き換え、dev/proc/キーの実マウント解除、環境削除、再実行、シンボリックリンク拒否を検証。
  稼働中のMirakurun環境を削除するテストは実施していません。
  再現用テストは `./tests/Test-Remove.ps1 -Serial <TVのADB接続先>` です。
  テストは `/data/local/tcl-mirakurun-delete-test` のみを削除対象にします。
- v0.1.2で、セットアップ成功後の5秒待機・自動再起動・Mirakurun自動復帰を実機で確認。
- v0.1.3でアプリ独自の有線維持処理を追加。既存BonDriver側の維持プロセスを停止した状態で
  eth0の169.254.95.200を一度削除し、約3秒以内のアドレス再取得と有線HTTP 200を確認。
  構築時の既存環境判定をファイル・フックの存在に変更し、一時的な状態取得失敗による
  既存の有線設定上書きを防止しました。

## 未確認・制限

- ネイティブ配信が一度も入っていないTVでの初回導入分岐は、この実機では未確認。
  対応機種以外では使用しないでください。
- 数時間～数日の連続運転、全登録局の映像・音声、Wi-Fi消灯時の長時間安定性は未確認。
- 選局直後の受信TSではFFmpegの初期ヘッダー警告や一部AACデコード警告が出ました。
  短い映像デコードの成功を、全期間・全音声の無エラー動作の保証とはしていません。
- 番組DBはMirakurun側で遅延保存されます。初回収集中の直後に再起動すると、
  未保存の番組情報は再収集が必要です。
- GitHub Actionsのビルド定義を用意していますが、この記録のAPKはローカルでビルドしました。

放送TSや実機の接続キー・署名秘密鍵は検証用データとして公開していません。

## 自動有線アドレスの検証（2026-11-03）

- 実機のEthernet設定がDHCPであることを読み取り確認。共通固定IPの維持を廃止。
- 同梱BusyBox zcipがARP確認後にリンクローカルアドレスを自動選択することを実機確認。
- 旧BonDriver側の固定エイリアス維持と競合しないよう、既知の旧スクリプトをバックアップして調整。
- Windowsの実有線IPを送信元に指定して、選択されたTV有線IPの `/api/status` がHTTP 200を返すことを確認。
- Wi-Fi側APIも引き続き応答。TVの再起動・Mirakurunサーバーの再起動は実施していない。
- DHCPあり／なし・ケーブルなし・DHCP専用・手動固定モードの6条件を模擬テスト。
- ルーターへの差し替え、実DHCPリース取得と競合機器を使ったARP衝突試験は未実施。
- 複数仮想NICがあるWindowsでは通常の経路選択で有線に到達しない場合があり、送信元を指定しない接続は別途確認が必要。

## .local接続の追加確認（2026-11-03）

- WindowsのDNSキャッシュが旧固定IPを保持し、リンクローカル宛ての通常経路がTailscaleを選択していたことを確認。
- 管理者権限でDNSキャッシュを消去し、現在のTVアドレスのみを対象とする `/32` 経路を実有線インターフェースへ追加。
  ActiveStoreのみの一時経路であり、PC再起動・TVのアドレス変更後には再設定が必要。
  アダプターの全体メトリックとデフォルト経路は変更していない。
- TVの稼働中Mirakurunにも管理対象mDNS名だけのOrigin許可を適用。
  アクティブストリームがないことを確認してMirakurunのみ再起動。
- OSの通常の名前解決と送信元を指定しないHTTPで、有線用 `.local` とWi-Fi用 `-wifi.local` の
  `/` と `/api/status` がいずれもHTTP 200。Origin・Refererを付けたAPIリクエストも成功。

## WindowsのDHCP予約による直結（2026-11-03）

- Windows専用サービスから登録したTVの有線MACへ、プライベート `/30` の同じIPを配布。
  TVのEthernet設定がDHCPのままであることと、実際のOFFER/ACK・アドレス取得を確認。
- 元のMirakurun許可設定が旧LANのみだったため、新しい直結IPからの要求が切断される問題を再現。
  現在のeth0に付いたプライベート `/30` の2ホストのみを追加許可して修正。
  LAN全体・外部IP・Wi-Fiの別ネットワークは追加許可しないことをモックテスト。
- 送信元指定や一時 `/32` 経路なしで、直結IPと `.local` の画面・APIがHTTP 200。
- Windowsサービスの再起動とTVのDHCP再取得後も同じIP。サービスの解除・再導入とPC有線のDHCP復元を確認。
- PC全体の再起動、長期間のリース更新、スリープ復帰は未実施。
